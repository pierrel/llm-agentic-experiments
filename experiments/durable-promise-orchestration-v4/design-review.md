# Durable-promise orchestration v4 design review

Review was completed before the v4 bundle is sealed or any v4 provider request
is made. The review record covers the actual committed candidate and runner,
not an earlier todo-rider proposal.

## Scientific integrity

Verified findings:

- V3 is incomplete: it preserves 16 provider-reaching episodes and a
  pre-provider interruption, but cannot be pooled with or treated as a baseline
  for v4. Resolution: v4 has fresh trial IDs/seeds and names v3 only as
  directional negative lineage.
- The lifecycle text must not equate a conditional future action with executing
  that action. Resolution: the literal C1 paragraph says to preserve condition
  and requested action in thread memory and not perform or claim the future
  action now.
- The rows are exposed. Resolution: v4 is explicitly an exploratory screen;
  only a successful fixed C1 can advance to an unseen confirmation bank.
- A marker-only exposure check is insufficient. Resolution: before a provider
  call, the worker renders both conditions and verifies the full literal rider,
  exact C0 remainder, sealed prompt digests, and sealed initial tool-schema
  digest. Every actual provider request repeats the full-text one-or-zero check.

## Statistical rigor

Verified findings:

- The unit is one independent fresh thread/sandbox. Server generation seeds are
  unsupported, so records are not presented as paired observations.
- N=3 per condition per row is a development screen, not a significance test.
  Resolution: complete all 18 episodes and require C1 >=7/9 full passes, C1-C0
  full >=2, no row full-pass deficit, and no aggregate routing or answer/honesty
  regression.
- Missing activation is behavioral evidence, not an exclusion. Resolution:
  admitted failures remain reason-coded outcomes; only pre-provider admission
  denial/corruption can retry the same ID.

## Agentic harness fit

Verified findings:

- The treatment belongs in the ordinary web-main async-lifecycle section, not a
  todo-specific middleware. Resolution: it is an opt-in render argument, does
  not alter tools, middleware types, graph, state, or lifecycle, and the old
  experimental middleware is deleted.
- Prompt/schema treatment must be known before model work. Resolution: a
  deterministic worker preflight seals and verifies C0/C1 static prompt and
  initial OpenAI-tool-schema digests before `run_episode` can mark or make a
  provider request.
- Only the worker command owns `resource run llm`. Resolution: the run command
  is invoked directly; `launch-intent` is retryable and a provider-bound marker
  never replays.

## Minimum adequate setup

Verified findings:

- The existing ordinary-web-main graph, local context fixture, fixed model,
  no-network boundary, and deterministic full-row oracle are necessary to
  isolate the claim. No added todo requirement, alternate agent architecture,
  or external dependency remains.
- The proven durable-memory C1 pair is the control. Resolution: the v4 bundle
  seals the outcome-v2 -> outcome-v1 C1 provenance and verifies the current
  Assist memory-prompt digest before provider work.
- Reused rows are sufficient only to reject/narrow this candidate. Unseen
  confirmation and representative regression remain mandatory before release.
