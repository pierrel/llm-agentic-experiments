## Causal question and conditions

On top of the exact C1 durable-memory guidance confirmed by
`durable-promise-outcome-v2`, does one concise general todo-layer rider improve
mixed-turn completion in ordinary web-main? `C0` uses the current C1 memory
guidance and normal framework todo prompt. `C1` differs only by the opt-in
`OutcomeChecklistMiddleware`, appended after that framework prompt:

> When one user turn has multiple independently valuable outcomes and you start
> tool, skill, or asynchronous work on one, use a short todo list with one
> outcome per item if that work could cause another to be missed. Mark each item
> complete only when the outcome is actually done, then reconcile the list before
> replying. The todo list tracks this turn; it does not replace any user-requested
> file, schedule, or durable thread-memory record.

The middleware owns no tool, state, routing, or lifecycle. C0 and C1 use the
same fresh sandbox/thread, ordinary web-main graph, main skills, async context
fixture, local Qwen endpoint, decoding, and private `/agent/memory.md`.

## Rows, outcome, and decision

The three copied rows are already exposed development evidence only. Each has a
current grounded answer and a later conditional action; no prompt mentions
tools, skills, paths, or expected routing. One unit is one fresh thread and
sandbox. Run three independent repetitions per condition per row, in the sealed
position-balanced schedule.

Primary full-row pass requires grounding/context lifecycle, correct local
answer, private post-result capture of the condition and action, and no
unsupported completion claim. Components report routing, answer/honesty,
persistence, todo use, and todo reconciliation. The task oracle explicitly
accepts `4` or `four` where that is the same condition; todo completion never
substitutes for thread memory.

This exploratory candidate advances only if C1 has at least 7/9 full passes,
has no row deficit of two or more versus concurrent C0, and uses its temporary
checklist in at least 7/9 rows. Once a provider request is made, timeout,
refusal, malformed behavior, missing todo, or missing durable state is recorded
and is never rerun. Admission denials and demonstrable pre-request corruption
are separately recorded and may retry the same scheduled ID.

V3 is not confirmation evidence. A successful screen requires a new v4
registration with unseen natural confirmation rows, fixed C0/C1 sample size,
row-stratified analysis, stability, and unrelated regression gates.
